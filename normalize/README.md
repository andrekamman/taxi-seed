# normalize

Rewrites historical TLC parquet files to conform to the latest schema, driven by a per-type curated YAML mapping. Data loss is a first-class error — the tool halts unless every discarded column or lossy cast has an explicit acknowledgment.

## Usage

```bash
# One command, three states:
uv run normalize yellow

# 1. First run — no mapping exists.
#    Analyzes raw data, writes normalize/mappings/yellow.yaml with SUGGESTED
#    renames + TODO acknowledgments, prints next-step instructions, exits 3.

# 2. Edit normalize/mappings/yellow.yaml:
#    - Uncomment SUGGESTED entries you accept, delete the rest.
#    - Fill in `ack_date:` for each TODO.

# 3. Re-run:
uv run normalize yellow

# 3a. If new drift shows up (e.g. TLC adds a column later), the tool amends the
#     mapping with new SUGGESTED/TODO items for the unresolved columns
#     (preserving your existing entries) and exits 1. Review and re-run.

# 3b. If everything is resolved, the tool normalizes and exits 0.

# Run all four types in one go:
uv run normalize
```

Requires the parquet mirror produced by the [downloader](../downloader/README.md) at `raw/<type>/<year>/*.parquet`. Writes to `raw-normalized/<type>/<year>/*.parquet`.

## Mapping file

Every data type has a mapping at `normalize/mappings/<type>.yaml`. `ack_date` is the only required field for `lossy_casts:` and `acknowledged_data_loss:` entries; `ack_by` and `reason` are optional but recommended for git-history documentation.

```yaml
# Generated by `normalize yellow` on 2026-07-22.
# Detected drift transitions:
#   2013-01 -> 2015-01: renamed pu_datetime->tpep_pickup_datetime; added PULocationID
#   2016-06 -> 2016-07: dropped pickup_latitude, pickup_longitude
#   2020-01 -> 2020-02: added congestion_surcharge
#   2023-01 -> 2023-02: added airport_fee

target: yellow_tripdata_2024-01.parquet
renames:
  pu_datetime: tpep_pickup_datetime
lossy_casts:
  passenger_count:
    from: DOUBLE
    to: BIGINT
    ack_date: 2026-07-21
acknowledged_data_loss:
  pickup_latitude:
    ack_date: 2026-07-21
```

## What runs automatically (no mapping needed)

- Columns always-null in historical data, missing from target → dropped
- Columns missing from historical data, present in target → filled with NULL
- Type widenings that cannot lose data (INT → BIGINT, VARCHAR(10) → VARCHAR(50), etc.)

## What triggers an error

- Historical column has non-null data, is missing from target, and has no `renames:` or `acknowledged_data_loss:` entry
- Type cast could lose data (range or precision) and there's no `lossy_casts:` entry with an `ack_date`

The tool amends the mapping YAML with SUGGESTED/TODO scaffolding for these unresolved cases and prints a consolidated report — nothing is written to `raw-normalized/` if any item is unresolved.

## Exit codes

- `0` — success (all files normalized, or all were already present).
- `1` — mapping incomplete; unresolved items reported; nothing written.
- `2` — configuration error (missing raw data, malformed mapping, target file not found).
- `3` — first run; scaffold generated; human review required before normalization can proceed.

## Options

- `--sample <N|N%>` — rows or percent sampled during the schema-drift rename verification that runs at scaffold generation and amendment. Default `100%` (full scan). Reduce only for very large datasets. Metadata-only checks and precision scans always full-scan regardless.

## Regenerating a scaffold from scratch

Delete the mapping file and re-run:

```bash
rm normalize/mappings/yellow.yaml
uv run normalize yellow
```
